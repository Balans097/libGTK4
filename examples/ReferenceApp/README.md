# GTK4Demo — образец разделения на модули

## Граф зависимостей (без циклов)

```
i18n.nim  ──────────────┐
   │                    │
   ▼                    ▼
config.nim         docmodel.nim ──▶ (libGTK4)
   │                    │  ▲
   │                    │  │
   │              fileio.nim
   │                    │  │
   ▼                    ▼  │
dialogs.nim ◀────────────┘
   │
   ▼
actions.nim
   │
   ▼
gui.nim ──▶ config.nim, i18n.nim
   │
   ▼
main.nim
```

Коротко: `i18n` и `fileio` ни от чего не зависят. `docmodel` зависит только
от `i18n` (для текстов) и от GTK. `dialogs` зависит от `docmodel`+`fileio`+`i18n`.
`actions` зависит от `dialogs`+`docmodel`+`fileio`+`i18n`. `gui` зависит от
`actions`+`config`+`i18n`. `main` — от `gui`+`config`+`i18n`.

Циклов нет нигде, кроме одного потенциального места: **actions.nim не
импортирует gui.nim**, хотя переключение языка должно перестраивать меню.
Это решено инверсией зависимости — публичная переменная-хук
`actions.onLanguageChanged: proc()`, в которую `gui.setupWindow`
кладёт указатель на свою `gui.rebuildMenuBar`, а `actions.switchLanguage`
только её дёргает. Этот приём стоит держать в голове на будущее: как
только логике нужно "попросить" GUI что-то сделать, а не наоборот —
не тяните туда импорт, заводите хук.

## Что за что отвечает

| Модуль        | Отвечает за                                          | НЕ должен содержать |
|---------------|-------------------------------------------------------|----------------------|
| `i18n.nim`    | таблицы переводов, `tr()`, определение локали          | GTK-код |
| `config.nim`  | app id, размеры окна, CSS                              | логику, GTK-вызовы |
| `docmodel.nim`| модель документа (буфер, путь, флаг изменений)         | диалоги, обработчики действий |
| `fileio.nim`  | чтение/запись файлов, `FileResult`                     | GTK, диалоги |
| `dialogs.nim` | построение диалоговых окон                             | файловый I/O напрямую (только вызывает fileio) |
| `actions.nim` | обработчики `GSimpleAction`, регистрация действий      | построение постоянных виджетов главного окна |
| `gui.nim`     | меню, редактор, статусбар, компоновка окна             | бизнес-логику действий |
| `main.nim`    | запуск приложения                                      | всё остальное |

## Отметка текущего языка в меню «Настройки»

Пункты "English"/"Русский" — теперь не два независимых действия, а
один stateful `GAction` — `app.language`, с состоянием-строкой
(`"en"`/`"ru"`). Каждый пункт меню ссылается на один и тот же action,
но с разным `target` (тоже `"en"`/`"ru"`, задаётся через
`g_menu_item_set_action_and_target_value`). Пока состояние действия
совпадает с target конкретного пункта, GTK сам рисует его отмеченным
(радио-точка слева от подписи) — это встроенное поведение GMenu, без
единой строчки кастомной отрисовки.

`actions.onLanguageAction` при активации читает код языка из
переданного `GVariant`, переключает язык и обновляет состояние
действия (`g_simple_action_set_state`) — именно эта строчка двигает
отметку. Действие регистрируется один раз в `registerActions` и живёт
всё время работы приложения, поэтому при пересборке меню
(`rebuildMenuBar`) GTK читает его текущее состояние заново и сразу
показывает верный пункт отмеченным.

Мелкая техническая деталь: `libGTK4.nim` не оборачивает
`G_VARIANT_TYPE_STRING`/`g_variant_type_new`, поэтому тип параметра
строится вручную — `cast[GVariantType]("s".cstring)`. Это не хак в
плохом смысле: в самом GLib `G_VARIANT_TYPE_STRING` — это буквально
`(const GVariantType *) "s"`, то есть ровно то же самое приведение
типа, просто сделанное в C-заголовках, а не в обёртке.

## Почему не переключался язык — и как исправлено

Меню строилось через «автоматическое» меню окна: модель отдавалась в
`gtk_application_set_menubar`, а показ включался
`gtk_application_window_set_show_menubar(win, TRUE)`. На бумаге замена
модели после показа окна должна обновлять и уже показанное меню — но
на практике для уже смонтированного `GtkApplicationWindow` это
обновление ненадёжно (виджет меню строится системой один раз и не
всегда переслушивает смену модели). Именно поэтому нажатие на
"English"/"Русский" меняло статусбар и заголовок (они обновляются
вручную, напрямую), но подписи самого меню оставались прежними.

Исправлено переходом на явный виджет: `GtkPopoverMenuBar`, созданный
из модели (`gtk_popover_menu_bar_new_from_model`) и вставленный первым
дочерним элементом в `buildMainLayout` — как обычная часть раскладки,
а не невидимая связь через свойство окна. `docmodel.AppState` хранит
`mainBox` (контейнер) и `menuBarWidget` (текущий виджет меню).
`gui.rebuildMenuBar()` при смене языка строит новый виджет, вставляет
его на то же место (`gtk_box_insert_child_after`) и удаляет старый
(`gtk_box_remove`) — то есть реальная замена виджета в дереве, а не
надежда на автоматическое обновление. `actions.onLanguageChanged`
теперь просто указывает на `gui.rebuildMenuBar` напрямую.

## Локализация

* Добавить строку — вписать ключ в обе таблицы (`stringsEN`, `stringsRU`)
  в `i18n.nim`. Если забыть добавить перевод — `tr()` вернёт сам ключ,
  а не упадёт, и недостающий перевод сразу видно в интерфейсе.
* Добавить язык — новая таблица `stringsXX`, новый вариант в `Lang`,
  новая ветка в `case` внутри `tr()`, пункт меню + `onLangXX` в
  `actions.nim`.
* Смена языка на лету перестраивает только виджет меню (см. раздел
  ниже) — весь остальной интерфейс просто заново читает `tr()` в тех
  местах, что уже обновляются вручную (заголовок окна, статусбар).

## Сверено с реальным libGTK4.nim (v1.3)

После того как появился исходник `libGTK4.nim`, код поправлен под
реальные сигнатуры:

- **`GTK_DIALOG_MODAL` не существует** — `gtk_message_dialog_new`
  принимает `flags: gint` (передаётся `0`); модальность у диалогов
  выставляется отдельно через `gtk_window_set_modal`, что уже и
  делалось в `runOpenDialog`/`runSaveAsDialog`/`runAboutDialog`.
- **`showInfoDialog`/`showErrorDialog`/`showWarningDialog` уже есть в
  самой библиотеке** (обёртки над `showMessageDialog` с разным
  `GtkMessageType`) — свои копии в `dialogs.nim` убраны, используются
  готовые. Заодно ошибки теперь показываются с настоящим
  `GTK_MESSAGE_ERROR`, а не переиспользованным `INFO`.
- **Перенос строк в `GtkTextView` задаётся `PangoWrapMode`**, а не
  `GtkWrapMode` — используется `PANGO_WRAP_WORD`.
- `g_menu_append`/`g_menu_item_new` действительно принимают `cstring`
  (не `string`) — везде, где значение приходит из `tr()` (не литерал),
  стоит явный `.cstring`.
- **Модуль `state.nim` переименован в `docmodel.nim`** — имя модуля
  совпадало с именем экспортируемой из него переменной `state`, из-за
  чего `state.window` в других файлах компилятор трактовал как поиск
  символа `window` в модуле `state`, а не как обращение к полю
  переменной, и падал с "undeclared identifier". Сама переменная
  `state` и весь синтаксис `state.window`/`state.docPath` не менялись —
  поменялось только имя файла-модуля, который её объявляет.

Если при сборке всплывёт что-то ещё за пределами этого списка — это,
как правило, точечное несовпадение типа параметра, а не признак
проблемы в разделении на модули.

## CSS

Сейчас `config.appCSS` — обычный строковый литерал. Когда тема
разрастётся, замените на:

```nim
const appCSS* = staticRead("theme.css")
```

— содержимое `theme.css` подставится на этапе компиляции, а сам CSS
можно будет редактировать отдельным файлом, не трогая `.nim`-код.
Для приложений с несколькими темами — `GResource` и
`gtk_css_provider_load_from_resource`.
